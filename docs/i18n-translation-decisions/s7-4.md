# S7.4 — Briefs bilingues frontend wiring

Phase 3 of S7.4 (S7.4 Phase 1 was the DB migration + translation script
on spore-poc; Phase 2 was the 39-brief batch backfill). This sprint
plumbs the EN payload through the spore-web frontend so `/en/...`
pages actually display the translated content.

## What is now wired

### Backend (types + DB)

- New `VulgarizationEn` type (mirror of `VulgarizationFr` but with the
  neutral key `title` instead of `title_fr` — the column itself is
  `vulgarization_data_en` so the inner JSON stays clean).
- `BriefRow` carries `vulgarization_data_en` (added to the
  `JSON_COLUMNS` parsing list).
- `briefRowToBrief` parses it into `vulgarization_en` on the `Brief`.
- `briefToTeaser` forwards it onto `BriefTeaser` so the client
  component can render it without a second DB hit.
- `briefMetaTitle` / `briefMetaDescription` / `briefOgDescription` now
  accept a `locale` argument and prefer the EN payload when
  `locale === 'en'`.

### BriefDetailClient (`/[locale]/briefs/[id]`)

- Default `lang` = `useLocale() === 'en' ? 'en' : 'fr'`.
- Default `tab` = `'recherche'` on `/en/`, `'comprendre'` on `/fr/`
  (see decision below).
- `headerTitle` resolves through the active language's vulgarisation
  payload, falling back to `sharpened.title`.
- The "Comprendre" tab now has three branches:
  - `lang === 'en' && vulgarization_en` → render the same five-section
    layout (hypothesis / why it matters / imagine that / concretely /
    what the reviewers say) from the EN payload.
  - `lang === 'fr' && vulgarization_fr` → existing FR five-section
    layout, unchanged.
  - Otherwise → the old summary-based fallback (only fires for legacy
    briefs that have neither vulgarisation payload — a no-op in
    production after Phase 2).
- Effective-language fallback: `effectiveLang` flips to the available
  payload when the user picks a language whose data is missing. The
  toggle keeps the user's choice; an `FR fallback` / `EN fallback`
  badge surfaces the substitution next to the toggle.

### Cards and search (`/[locale]/briefs`)

- `EditorialBriefCard` picks `vulg_en.title` / `vulg_en.imagine_that`
  on `/en/` and falls back across languages so legacy briefs stay
  rendered.
- `BriefsClient.briefHaystack` now indexes both FR and EN payloads in
  the same lowercased blob — the search box matches whichever locale
  the user types in, regardless of the page's locale.

### SEO

- `briefMetaTitle` / `briefMetaDescription` / `briefOgDescription` are
  locale-aware.
- Sitemap was already bilingual (S7.2 + S7.3-residual-fix added it for
  `/[locale]/briefs/[id]` in the earlier `bilingualEntries()` helper).
  Verified: 38 briefs × 2 locales = 76 brief entries with
  `xhtml:link rel="alternate"` annotations on every row.

## Decisions

### Default tab follows the page locale

On `/en/`, the default tab is **Research**. The argument:

- The Research tab carries technical content that was already EN-native
  (sharpened title, formal predictions, references, panel review).
  No translation overhead, no risk of vulgarisation drift.
- The Understand tab is built from `vulgarization_en`, which is a
  high-quality but inevitably less authoritative LLM-translated layer
  on top of the FR vulgarisation. An EN visitor browsing for technical
  signal benefits from landing on the source-of-truth content.
- The user can flip in one click — the tab control is right there.

On `/fr/`, the default tab stays **Understand** because the FR
vulgarisation is the editorial signature for the FR audience.

The earlier hardcoded `tab='comprendre'` default applied to both
locales; that is what changed.

### `effectiveLang` and the fallback badge

`vulgarization_en` is filled for every brief published before this
sprint (Phase 2 backfill ran clean on 40 briefs). New briefs land with
FR only until the post-fire pipeline is updated to translate at
generation time (Phase 4, deferred). Until then, an `/en/` visitor
landing on a freshly published brief would see an empty Comprendre tab
without the fallback.

The fallback design:

- The toggle keeps the user's expressed choice (no silent override).
- `effectiveLang` resolves to the available payload. Content + section
  labels follow `effectiveLang`.
- A small `FR fallback` (or `EN fallback`) chip next to the toggle
  surfaces the substitution and explains why on hover.

This stays out of the way for the 40-brief baseline (where every
brief has both languages) but degrades gracefully when a new brief
ships before its EN translation lands.

### Search index includes both locales

`briefHaystack` could have been locale-conditional but two FR+EN
copies in the same blob is simpler, and it lets a user typing
"métalloprotéines" on `/en/briefs` still find the right brief, and
vice versa. The cost is ~5 KB extra haystack per brief, paid once at
mount in a `useMemo` — well below the threshold that would justify
the extra plumbing.

### Section labels follow `effectiveLang`, not page locale

The five Comprendre section headers ("L'hypothèse en quelques mots",
"Why it matters", etc.) are hardcoded inside each render branch
because they pair tightly with the content language. If the user is
reading FR content (lang='fr' or fallback), the headers should be FR
too — switching them to EN would mix registers in a single view.

## Things deferred

- **Brief detail Recherche tab section labels** ("Panel review",
  "Counter-evidence", quantitative prediction headers, etc.) are
  still localised via `t('briefDetailPage.section_*')` from the page
  locale, not `effectiveLang`. That is intentional: the Recherche
  content itself is EN-native (sharpened, panel reviews, evidence)
  for every brief, so the labels matching the page chrome locale is
  the right call. Only the Comprendre tab carries the dual-language
  payload.
- **Stub briefs** still render via `StubBriefClient` with hardcoded
  FR copy. They are rare, user-specific, and intentionally noindex;
  the bilingual-content scope leaves them alone.
- **`/en/briefs` brief ordering** — the sort uses panel consensus or
  novelty, locale-agnostic. Locale-specific ordering (e.g. surface
  briefs whose EN translation exists on /en/, drop FR-only briefs)
  is unnecessary post-Phase-2 since every brief has both.
- **Bold-markdown leak in one EN title** — `SPR-2026-FBF3` has its
  EN title saved as `**Intelligent stem cells…**` (markdown bold
  brackets the entire title, even though the FR source has no
  emphasis). The rendering path is correct; the data has a
  translator deviation. To fix: either `UPDATE` the column manually,
  or add a leading/trailing `**` strip in the translation script
  and re-run on this brief with `--force`. Single-brief issue, not
  systemic — out of Phase 3 scope.

## Phase 4 hand-off notes

The backfill column is wired end-to-end. When Phase 4 kicks in
(post-fire pipeline writes EN at generation time):

- The translation prompt + per-field voice guidance is already in
  `scripts/translate_brief_vulgarization.py`. Easiest reuse path:
  call the same `translate_brief()` async helper from inside the
  post-fire LangGraph subgraph after the FR vulgarisation step.
- The `effectiveLang` fallback will keep working — newly published
  briefs that haven't been processed by the translator yet will
  surface the FR-only badge until the next translation pass picks
  them up. No code change needed.
